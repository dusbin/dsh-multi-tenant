# DeepSeek Harness 多租户插件 — 设计方案（v0 草案）

> 状态：**草案（待评审）**。本文档在收到三项架构调研（`docs/research/01/02/03`）后补充定稿。
> 项目：`workspace/robinddu/dsh-multi-tenant`（git 管理，独立仓库）

---

## 1. 项目概述

为 DeepSeek Harness（DSH）`web` profile 开发一个**多租户插件**，把 DSH 从"本地单用户开发工具"扩展为"可多人登录、按角色使用、可计量计费、可审计"的服务形态。

### 1.1 核心目标

| 目标 | 说明 |
|---|---|
| 权限分离 | 三角色：**管理员 / 审计员 / 使用者**，细粒度权限矩阵 |
| 登录 | 邮箱密码（v1 必做）+ LDAP（v1.5）+ SSO/OIDC（v2），可多方式并存 |
| 管理员能力 | 启停账号、token/金额限额、角色分配（含审计角色权限）、审计日志查看、用量统计 |
| 统计 | 每用户/每租户的会话数、请求数、token 消耗、金额、时间分布 |
| 审计 | 登录/登出、管理操作、配额变更、越权尝试全程留痕 |
| 多租户 | 租户隔离（数据、配额、统计按租户归属），v1 单实例部署 |

### 1.2 非目标（v1 不做）

- 进程级/文件系统级强隔离（每个租户独立 profile/容器）——v1 为"同一 host 进程内按用户隔离会话与权限"，文件系统隔离依赖 DSH 现有 sandbox 能力评估后定
- 多机 HA / 分布式部署
- SAML / 微信等小众 SSO 协议
- 计费账单支付（仅做用量统计与金额折算）

## 2. DSH 架构现状（调研结论）

> 详细证据见 `docs/research/*.md`（三项调研进行中）。

### 2.1 插件模型

- DSH 由 **profile** 定义运行形态；profile = 插件组合包（bundle）patch 层 + 用户 `cordis.patch.yml` 覆盖层
- 插件是 **Cordis 4** 插件：`apply(ctx, config)`、服务注册（`ctx.xxx`）、`inject` 依赖注入、事件系统
- 插件分 **host 半**（node 进程内）与 **client 半**（浏览器内，React）——双半插件体系
- 前端 Web shell 是 Vite 构建的 SPA，由 `dsh-web-app` 提供 dist；浏览器插件名录（`dsh.client` roster）扫描进 `window.__DSH_BOOT__`

### 2.2 传输与信任模型（关键）

- 浏览器 ↔ host：HTTP POST `/api`（unary RPC）+ 两条 WebSocket 下行流 `/api/events.mux`、`/api/events.host`
- **当前没有任何认证层**：`/api` 信任栅栏（loopback + `trustedHosts`）只是 DNS rebinding/跨站防御（可达性策略，非认证）
- `dsh-host-webserver` 绑定 host 只接受 `127.0.0.1` / `0.0.0.0`；CLI 在 `--host 0.0.0.0` 时**拒绝启动**（"远程访问具备认证层之前有意不支持"）
- DSH 官方立场：生产部署加固 = **前置反向代理**（TLS/认证），不在 v1 内置
- `/api` 处理链：`trust fence → HTTP bridge → Typert interceptor（认领 Remote endpoint）→ apiProxy fallback`；`settings.*`/`credentials.*`/`host.*` 等**特权方法**额外钉死 loopback
- WS upgrade 由 connection 插件注册，同样先过 trust fence

### 2.3 会话与计量（现成抓手）

- `ctx.sessions.create(id, { seed, meta })` —— **`meta` 可携带归属信息（owner=userId）**，会话 header 可扩展
- 会话事件日志：`assistant/chunk { type: 'usage' }` 记录每步用量；回退 `assistant/message.usage`；含 provider/model 溯源
- `ctx.tokenMeter.measure()` / `estimateMessage()`：回放感知的 token 测量服务；`tokenUsage` 会话投影提供 `uncachedInputTokens / outputTokens / cacheReadTokens / cacheWriteTokens`
- **没有现成价格表**：金额折算需插件自维护模型价格表（可配置）

### 2.4 存储

- **Node 24 内置 `node:sqlite` 可用（已实测，零原生依赖）**——适合存用户/配额/用量/审计等关系数据
- `dsh-storage-domain` 是 KV 领域存储（JSON 后端），**无跨表事务/二级索引**，不适合做主数据 → 插件自建 SQLite（profile 数据目录下）

### 2.5 插件开发与安装（实测）

- profile 目录：`$DSH_HOME/profiles/<name>`（本机 `~/.dsh/profiles/web`），含 `package.json`（`dsh.profile.bundles` 有序组合包列表）、`cordis.patch.yml`（用户 patch 层）、`cordis.yml`（`[]` 空条目根）
- **插件三种接入方式（本机已有先例）**：
  1. patch 行直接指向**绝对路径源码文件**（如 `scratch-plugin/src/knowledge-base.mjs?v=2`，`?v=` 破除 ESM 缓存免重启）
  2. **软链到 profile node_modules**（如 `voice-plugin`：`~/.dsh/profiles/web/node_modules/dsh-voice -> 插件目录`），patch 行写包名
  3. `dsh plugin --profile web <pnpm args>`（publish 后正规安装）
- **双半插件形态**（voice-plugin 为范本）：host 半 = 普通 ESM 模块（导出 `name/inject/apply`）；client 半 = 手写 bundle `window.__ModuleLoader__.load({id, factory})`（`require('react')` 由浏览器模块表解析，**无需构建工具链**）
- 实测：本机 web 实例在线（127.0.0.1:3080）；`host.describe` 返回 `{version, cwd, provider, model, attachedSessions, home, canOpenPath}`——**无任何身份概念**；RPC envelope：请求 `{rpcId, type:'client-request', method, payload}` → 响应 `{type:'server-response', rpcId, result:{ok, value}}`

## 3. 总体架构

```
                 ┌──────────────────────────────────────────────┐
  浏览器          │  DSH web profile（单一 host 进程）             │
 ┌────────┐      │ ┌──────────────────────────────────────────┐ │
 │ 登录页  │─────▶│ │ 认证网关 (dsh-multi-tenant host 半)       │ │
 │ 控制台  │      │ │  · 会话校验(HttpOnly Cookie)              │ │
 │ 聊天UI  │      │ │  · RBAC 检查                             │ │
 └────────┘      │ │  · 配额检查                              │ │
                 │ └──────────────────────────────────────────┘ │
                 │  /api 处理链（trust fence → gateway → proxy）│
                 │  WS 下行流（events.mux / events.host）       │
                 │  ctx.sessions / tokenMeter / api-remotes     │
                 │  ┌────────────────────────────────────────┐  │
                 │  │ 多租户数据层（SQLite）                    │  │
                 │  │ users/roles/tenants/quotas/usage/audit  │  │
                 │  └────────────────────────────────────────┘  │
                 └──────────────────────────────────────────────┘
                                    ▲
              （推荐）反代 TLS：nginx/caddy → 127.0.0.1:3080
```

### 3.1 部署形态

- **形态 A（推荐）**：DSH 绑定 `127.0.0.1`，前置反向代理（nginx/caddy）终结 TLS；插件认证网关在 DSH 进程内把关。信任栅栏通过 `--trusted-host <域名>` 或反代 Host 传递适配
- **形态 B**：插件自带公网监听端口 + 内嵌 HTTP/WS 反代（绑定 `0.0.0.0`，TLS 可选），网关与代理合一 —— 适合无现成反代的内网直连场景
- 两种形态的**认证逻辑完全一致**，网关是同一套；差异只在"谁来监听公网端口"

### 3.2 认证网关插入点（技术关键，需调研确认）

- 候选 1：**包装 `ctx.webServer` 服务**（re-provide 包装版 register/registerUpgrade，所有 /api 与 WS upgrade 先过会话校验）——不 fork 任何 DSH 包，但依赖 Cordis 激活顺序
- 候选 2：**自建公网端口内嵌反代**（形态 B），在插件自己的 HTTP 层把关——与 Cordis 顺序无关，最稳，但代码量多（~反代实现）
- 候选 3：`ctx.connection.rpc.intercept('/api', …)` —— 已确认 **RPC handler 看不到 HTTP 头**，无法取 cookie，**不可行**
- 结论：候选 1 优先（若激活顺序可控），候选 2 兜底

### 3.3 登录会话模型

- 登录成功 → 服务端签发会话（`auth_sessions` 表存 token 哈希）→ `HttpOnly + Secure + SameSite=Lax` Cookie
- WS upgrade 同样校验 Cookie（网关统一处理）
- 登出/过期/管理员禁用账号 → 会话立即失效
- 防爆破：登录速率限制 + 失败锁定

## 4. 数据模型（SQLite schema 草案）

```
tenants        id, name, status(active/disabled), config(json), created_at
users          id, tenant_id→tenants, username, email, password_hash, ldap_dn,
               status(active/disabled), role(admin|auditor|user), created_at,
               last_login_at, last_login_ip
quotas         id, scope(global|tenant|user), target_id, token_limit,
               amount_limit, currency, period(daily|monthly|total),
               hard_limit(bool), created_at, updated_at
usage_records  id, ts, tenant_id, user_id, session_id, model, provider,
               input_tokens, output_tokens, cache_read_tokens,
               cache_write_tokens, cost, request_count
session_meta   session_id, user_id, tenant_id, title, created_at, ended_at,
               message_count, token_total, cost_total   -- 会话级聚合(可派生)
auth_sessions  id, user_id, token_hash, created_at, expires_at, ip, user_agent
audit_logs     id, ts, actor_user_id, tenant_id, action, target_type,
               target_id, detail(json), result(success|denied), ip
price_table    model, provider, input_price, output_price, currency  -- 可配置
```

> 细节（索引、迁移、upsert 策略）在实现阶段定稿；迁移用 SQLite `user_version`。

## 6. 用量统计与计价

### 6.1 采集链路

1. 会话创建时写入 `session.header.meta.owner = userId`（归属）
2. 订阅会话事件（`assistant/chunk usage` / `assistant/message.usage`）或读取 `tokenUsage` 投影 → 累计
3. 会话关闭/定期 flush → 写 `usage_records`（按日聚合 + 会话级明细）

### 6.2 计价

- 插件内置模型价格表（DeepSeek 官方价作默认，管理员可改/增自定义模型）
- `cost = input_tokens × input_price + output_tokens × output_price + cache 区分计价`
- 金额单位可配置（CNY/USD）；"token/金额限额"按统一口径折算

### 6.3 统计视图

- 按 用户 / 租户 / 日期 / 模型 聚合：会话数、请求数、token（输入/输出/缓存）、金额、活跃度
- 会话明细：时间、模型、token、金额、消息数

## 7. UI 设计（client 半插件）

| 界面 | 受众 | 内容 |
|---|---|---|
| 登录页（全屏门禁，shell 装配前） | 所有人 | 邮箱密码 / LDAP / SSO 按钮、错误提示、首启 bootstrap 引导 |
| 管理控制台 | 管理员 | 用户管理（CRUD/启停/角色）、配额设置、价格表、审计日志浏览、用量统计 |
| 审计视图 | 审计员 | 只读统计 + 审计日志 |
| 个人中心 | 使用者 | 个人用量、配额剩余、会话历史 |
| 顶部/侧边栏入口 | 按角色 | 控制台入口、登出 |

> 门禁实现：client 插件首屏判断"已登录"（`/api/auth/me`），未登录渲染登录页，不装配聊天 UI；服务端网关同步强制（防止绕过）。

## 8. 插件工程结构（草案）

```
dsh-multi-tenant/
├── package.json          # dsh manifest：host + client 双半
├── cordis.patch.yml      # 组合 patch：插入 host/client 行
├── tsconfig.json
├── src/
│   ├── host/
│   │   ├── index.ts      # 主插件 apply：装配网关、服务、DB

│   │   ├── auth/         # local / ldap / oidc 登录策略
│   │   ├── rbac.ts       # 权限矩阵与校验
│   │   ├── quota.ts      # 配额检查与强制
│   │   ├── metering.ts   # 用量采集与计价
│   │   ├── audit.ts      # 审计日志
│   │   ├── db/           # SQLite（node:sqlite）schema + DAO

│   └── client/
│       ├── index.tsx     # client 插件：门禁/控制台/个人中心
│       └── components/…
```

- 配置 schema：schemastery/zod；默认值出厂可用（bootstrap 管理员）

## 10. 风险与待决策点

1. **认证网关插入方式**：webServer 包装（依赖激活顺序，需验证）vs 内嵌反代（稳但代码多）
2. **远程访问**：0.0.0.0 绑定的放开方式（改配置/包装 startup/反代）
3. **租户模型语义**：真多租户（租户间全隔离）还是"多用户单租户"起步 —— 需用户确认
4. **隔离深度**：v1 会话/权限/数据层隔离；文件系统/进程隔离评估后定
5. **"管理员有审计角色权限"** 语义确认（管理员继承审计权限 vs 可授予他人审计角色）
6. **计价口径**：默认价格表（DeepSeek 官方价）+ 币种
7. **DB**：node:sqlite（已定，风险低）
