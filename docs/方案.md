# DeepSeek Harness 多租户插件 — 设计方案（v1.0）

> 状态：**待评审**。三项架构调研已完成两项（01 Web UI / 03 身份会话计量），03 项（host 端插件架构）完成后合并定稿。
> 项目：`workspace/robinddu/dsh-multi-tenant`（git 管理，独立仓库）

---

## 1. 项目概述

为 DeepSeek Harness（DSH）`web` profile 开发一个**多租户插件**，把 DSH 从"本地单用户开发工具"扩展为"可多人登录、按角色使用、可计量计费、可审计"的服务形态。

### 1.1 核心目标

| 目标 | 说明 |
|---|---|
| 权限分离 | 三角色：**管理员 / 审计员 / 使用者**，细粒度权限矩阵 |
| 登录 | 邮箱密码（v1 必做）+ LDAP（v1.5）+ SSO/OIDC（v2），可多方式并存 |
| 管理员能力 | 启停账号、token/金额限额、角色分配（含审计角色权限）、审计日志查看、用量统计 |
| 统计 | 每用户/每租户的会话数、请求数、token 消耗、金额、时间分布 |
| 审计 | 登录/登出、管理操作、配额变更、越权尝试全程留痕 |
| 多租户 | 租户隔离（数据、配额、统计按租户归属），v1 单实例部署 |

### 1.2 非目标（v1 不做）

- 进程级/文件系统级强隔离（每个租户独立 profile/容器）——v1 为"同一 host 进程内按用户隔离会话与权限"，文件系统隔离依赖 DSH 现有 sandbox 能力评估后定
- 多机 HA / 分布式部署
- SAML / 微信等小众 SSO 协议
- 计费账单支付（仅做用量统计与金额折算）

## 2. DSH 架构现状（调研结论）

> 详细证据见 `docs/research/*.md`（三项调研进行中）。

### 2.1 插件模型

- DSH 由 **profile** 定义运行形态；profile = 插件组合包（bundle）patch 层 + 用户 `cordis.patch.yml` 覆盖层
- 插件是 **Cordis 4** 插件：`apply(ctx, config)`、服务注册（`ctx.xxx`）、`inject` 依赖注入、事件系统
- 插件分 **host 半**（node 进程内）与 **client 半**（浏览器内，React）——双半插件体系
- 前端 Web shell 是 Vite 构建的 SPA，由 `dsh-web-app` 提供 dist；浏览器插件名录（`dsh.client` roster）扫描进 `window.__DSH_BOOT__`

### 2.2 传输与信任模型（关键）

- 浏览器 ↔ host：HTTP POST `/api`（unary RPC）+ 两条 WebSocket 下行流 `/api/events.mux`、`/api/events.host`
- **当前没有任何认证层**：`/api` 信任栅栏（loopback + `trustedHosts`）只是 DNS rebinding/跨站防御（可达性策略，非认证）
- `dsh-host-webserver` 绑定 host 只接受 `127.0.0.1` / `0.0.0.0`；CLI 在 `--host 0.0.0.0` 时**拒绝启动**（"远程访问具备认证层之前有意不支持"）
- DSH 官方立场：生产部署加固 = **前置反向代理**（TLS/认证），不在 v1 内置
- `/api` 处理链：`trust fence → HTTP bridge → Typert interceptor（认领 Remote endpoint）→ apiProxy fallback`；`settings.*`/`credentials.*`/`host.*` 等**特权方法**额外钉死 loopback
- WS upgrade 由 connection 插件注册，同样先过 trust fence

### 2.3 会话与计量（现成抓手）

- `ctx.sessions.create(id, { seed, meta })`；`SessionId` 是任意品牌字符串 → **归属用 id 前缀编码（`u-<userId>-s-<uuid>`）+ 插件映射表**（`meta` 无自由扩展字段）
- 会话事件日志：`assistant/chunk { type: 'usage' }` 记录每步真实用量（适配器上报）；回退 `assistant/message.usage`；含 provider/model 溯源
- `ctx.tokenMeter.measure()` / `estimateMessage()`：回放感知的 token 测量服务；`tokenUsage` 会话投影提供四桶 `uncachedInputTokens / outputTokens / cacheReadTokens / cacheWriteTokens`（互不重叠）
- **没有现成价格表**（`resolveModelInfo` 只有 context window）：金额折算需插件自维护模型价格表（可配置）

### 2.4 存储

- **Node 24 内置 `node:sqlite` 可用（已实测，零原生依赖）**——适合存用户/配额/用量/审计等关系数据
- `dsh-storage-domain` 是 KV 领域存储（JSON 后端），**无跨表事务/二级索引**，不适合做主数据 → 插件自建 SQLite（profile 数据目录下）

### 2.5 插件开发与安装（实测）

- profile 目录：`$DSH_HOME/profiles/<name>`（本机 `~/.dsh/profiles/web`），含 `package.json`（`dsh.profile.bundles` 有序组合包列表）、`cordis.patch.yml`（用户 patch 层）、`cordis.yml`（`[]` 空条目根）
- **插件三种接入方式（本机已有先例）**：
  1. patch 行直接指向**绝对路径源码文件**（如 `scratch-plugin/src/knowledge-base.mjs?v=2`，`?v=` 破除 ESM 缓存免重启）
  2. **软链到 profile node_modules**（如 `voice-plugin`：`~/.dsh/profiles/web/node_modules/dsh-voice -> 插件目录`），patch 行写包名
  3. `dsh plugin --profile web <pnpm args>`（publish 后正规安装）
- **双半插件形态**（voice-plugin 为范本）：host 半 = 普通 ESM 模块（导出 `name/inject/apply`）；client 半 = 手写 bundle `window.__ModuleLoader__.load({id, factory})`（`require('react')` 由浏览器模块表解析，**无需构建工具链**）
- 实测：本机 web 实例在线（127.0.0.1:3080）；`host.describe` 返回 `{version, cwd, provider, model, attachedSessions, home, canOpenPath}`——**无任何身份概念**；RPC envelope：请求 `{rpcId, type:'client-request', method, payload}` → 响应 `{type:'server-response', rpcId, result:{ok, value}}`

## 3. 总体架构

```
                 ┌──────────────────────────────────────────────┐
  浏览器          │  DSH web profile（单一 host 进程）             │
 ┌────────┐      │ ┌──────────────────────────────────────────┐ │
 │ 登录页  │─────▶│ │ 认证网关 (dsh-multi-tenant host 半)       │ │
 │ 控制台  │      │ │  · 会话校验(HttpOnly Cookie)              │ │
 │ 聊天UI  │      │ │  · RBAC 检查                             │ │
 └────────┘      │ │  · 配额检查                              │ │
                 │ └──────────────────────────────────────────┘ │
                 │  /api 处理链（trust fence → gateway → proxy）│
                 │  WS 下行流（events.mux / events.host）       │
                 │  ctx.sessions / tokenMeter / api-remotes     │
                 │  ┌────────────────────────────────────────┐  │
                 │  │ 多租户数据层（SQLite）                    │  │
                 │  │ users/roles/tenants/quotas/usage/audit  │  │
                 │  └────────────────────────────────────────┘  │
                 └──────────────────────────────────────────────┘
                                    ▲
              （推荐）反代 TLS：nginx/caddy → 127.0.0.1:3080
```

### 3.1 部署形态

- **形态 A（推荐）**：DSH 绑定 `127.0.0.1`，前置反向代理（nginx/caddy）终结 TLS；插件认证网关在 DSH 进程内把关。信任栅栏通过 `--trusted-host <域名>` 或反代 Host 传递适配
- **形态 B**：插件自带公网监听端口 + 内嵌 HTTP/WS 反代（绑定 `0.0.0.0`，TLS 可选），网关与代理合一 —— 适合无现成反代的内网直连场景
- 两种形态的**认证逻辑完全一致**，网关是同一套；差异只在"谁来监听公网端口"

### 3.2 认证网关插入点（技术关键，已部分验证）

- 候选 1：**包装 `ctx.webServer` 服务**（re-provide 包装版 register/registerUpgrade，所有 /api 与 WS upgrade 先过会话校验）——不 fork 任何 DSH 包；`ctx.webServer` 是普通 Cordis 服务（`register`/`registerUpgrade`/`registerFallback`），Cordis 提供 `ctx.inject` 回调作用域 + service 可替换语义，**可行性依赖激活顺序**（待报告 02 确认细节）
- 候选 2：**自建公网端口内嵌反代**（形态 B），在插件自己的 HTTP 层把关——与 Cordis 顺序无关，最稳，但代码量多（~反代实现）
- 候选 3：`ctx.connection.rpc.intercept('/api', …)` —— 已确认 **RPC handler 只收到 `(endpoint, payload, signal)`，看不到 HTTP 头**，无法取 cookie，**不可行**
- 辅助事实（已确认）：`WebServer` 配置 `host` 仅接受 `127.0.0.1|0.0.0.0`；**CLI 的 `--host 0.0.0.0` 拒绝只作用于 flag 解析路径**——通过 patch/env 覆盖 `webserver` 行配置绑定 `0.0.0.0` 合法可行；绑定后 `webRuntime` 自动推导 LAN IP 字面量进信任栅栏（LAN 场景）
- 结论：候选 1 优先（若激活顺序可控），候选 2 兜底；部署上形态 A（反代）始终成立

### 3.3 登录会话模型

- 登录成功 → 服务端签发会话（`auth_sessions` 表存 token 哈希）→ `HttpOnly + Secure + SameSite=Lax` Cookie
- WS upgrade 同样校验 Cookie（网关统一处理）
- 登出/过期/管理员禁用账号 → 会话立即失效
- 防爆破：登录速率限制 + 失败锁定

## 4. 数据模型（SQLite schema 草案）

```
tenants        id, name, status(active/disabled), config(json), created_at
users          id, tenant_id→tenants, username, email, password_hash, ldap_dn,
               status(active/disabled), role(admin|auditor|user), created_at,
               last_login_at, last_login_ip
quotas         id, scope(global|tenant|user), target_id, token_limit,
               amount_limit, currency, period(daily|monthly|total),
               hard_limit(bool), created_at, updated_at
usage_records  id, ts, tenant_id, user_id, session_id, model, provider,
               input_tokens, output_tokens, cache_read_tokens,
               cache_write_tokens, cost, request_count
session_meta   session_id, user_id, tenant_id, title, created_at, ended_at,
               message_count, token_total, cost_total   -- 会话级聚合(可派生)
auth_sessions  id, user_id, token_hash, created_at, expires_at, ip, user_agent
audit_logs     id, ts, actor_user_id, tenant_id, action, target_type,
               target_id, detail(json), result(success|denied), ip
price_table    model, provider, input_price, output_price, currency  -- 可配置
```

> 细节（索引、迁移、upsert 策略）在实现阶段定稿；迁移用 SQLite `user_version`。

### 4.1 存储选型（已确认）

- **主数据（users/quotas/usage/audit）用 `node:sqlite`**（Node 24 内置，实测可用，零 native 依赖；参考 `dsh-session-query-sqlite` 的用法：专用派生库、单进程单所有者、WAL）
- `ctx.storage.domain`（KV 领域存储）**不做主数据**（无跨表事务/二级索引），可作辅助（如热缓存/进程内同步）
- DB 文件位置：profile 数据目录（`$DSH_HOME/profiles/web/` 下或 `dshHomePath('multi-tenant')`），目录权限 0700/0600
- 单进程单所有者：多 host 进程共享同一 DB 不受支持（DSH 存储形态同理）

### 4.2 会话归属（已确认的机制）

- `SessionHeader.meta` **没有自由扩展字段**（仅 `cwd/parentSession/createdAt/seedLength/origin/delegationDepth/agentPreset`）→ 不能塞 `userId`
- `SessionId` 是任意品牌字符串 → **用前缀编码归属**：`u-<userId>-s-<uuid>`，配合插件映射表 `userId ↔ sessionIds`
- 会话创建由 Host 侧 `ctx.sessions.create(id, {meta})` 完成 → 网关/服务层在创建时强制注入归属前缀，防止客户端伪造他人前缀

## 6. 用量统计与计价

### 6.1 采集链路（已确认）

1. 会话创建：网关/服务层强制 `SessionId = u-<userId>-s-<uuid>`，并登记 `userId ↔ sessionId` 映射（DB）
2. 真实用量：适配器流上发 `usage` 分片 → 会话日志 `assistant/chunk {type:'usage'}`（回退 `assistant/message.usage`）→ 读取 `ctx.tokenMeter.measure()` 或 `tokenUsage` 投影四桶（`uncachedInput/output/cacheRead/cacheWrite`，互不重叠）
3. 记账时机：**每次 `assistant/chunk usage` 提交时记账最准**（失败请求也可能有 usage 分片）；按 `(provider, model)` 匹配价格表 → 累加到用户/租户周期配额与用量表
4. 会话关闭/定期 flush → 写会话级聚合（消息数、token 合计、金额合计、时长）

### 6.2 计价（已确认无现成价格表）

- `ctx.llm.resolveModelInfo()` **只有 context window / defaultMaxTokens / reasoning，无价格字段** → 金额必须自建价格表
- 插件内置模型价格表（DeepSeek 官方价作默认，管理员可改/增自定义模型；`(provider, model)` 匹配）
- `cost = uncachedInput × input_price + output × output_price + cacheRead × cache_price + cacheWrite × cache_price`（缓存价可配置，默认 0.1×/1× 类策略）
- 金额单位可配置（CNY/USD）；"token/金额限额"按统一口径折算

### 6.3 统计视图

- 按 用户 / 租户 / 日期 / 模型 聚合：会话数、请求数、token（输入/输出/缓存）、金额、活跃度
- 会话明细：时间、模型、token、金额、消息数

## 7. UI 设计（client 半插件）

| 界面 | 受众 | 内容 |
|---|---|---|
| 登录页（全屏门禁） | 所有人 | 邮箱密码 / LDAP / SSO 按钮、错误提示、首启 bootstrap 引导 |
| 管理控制台 | 管理员 | 用户管理（CRUD/启停/角色）、配额设置、价格表、审计日志浏览、用量统计 |
| 审计视图 | 审计员 | 只读统计 + 审计日志 |
| 个人中心 | 使用者 | 个人用量、配额剩余、会话历史 |
| 侧栏/设置入口 | 按角色 | 控制台入口、登出 |

### 7.1 槽位落位（已确认的机制）

- **登录门禁（UX 层）**：注册 `shell.overlay`（list 槽、root 作用域、全屏浮层）——组件读取 `ctx.connection.hostDescription`/自建 auth 状态（`/api/auth/me`），未认证时渲染登录表单并 opt-in 指针事件（overlay 默认 click-through）；登录成功后整页刷新重建连接。`root` 槽官方**禁止**注册（会遮蔽 AppFrame）；`conversation` 等 single 槽注册会替换现有表面——均不可用
- **门禁真值（安全层）**：宿主侧 webserver 路由中间件（认证网关）——**唯一能真正拦住未认证请求的层**；客户端 overlay 只是 UX
- **控制台/统计/审计页**：注册 `settings.section`（list 槽，一 feature 一页，`{id, order, label}`）→ 设置面板内多页签（参考 `dsh-client-ui-settings-models` 的注册范式）
- **侧栏入口**：`sidebar.footer.action`（list 槽，设置旁的附加操作位）
- **首启引导**：`settings.onboarding`（list 槽，bootstrap 管理员向导）
- **⚠️ settings 写路径 loopback-only**：`settings.*`/`credentials.*`/`host.*`/`agentPreset.*` 是特权方法，远程（非 loopback）客户端 403 → **管理控制台的数据 API 不走 settings 命名空间**，走插件自建 RPC 通道
- **自建 RPC 通道（已确认机制）**：宿主侧 `ctx.connection.rpc.handle('/mt', handler, {authority})` 注册自定义通道（webserver 上挂 prefix 路由、过信任栅栏）；客户端 `ctx.connection.rpc.call('/mt', endpoint, payload)` ——管理/租户 API 全部走此通道（含认证+RBAC+配额检查，handler 内自建；通道信任策略只有 `trusted-host|loopback` 两档，"已认证"由我们自建）
- **客户端不能运行时注册 Typert namespace**（能力集构建期固定）——不依赖 `ctx.remote` 扩展；**控制台用静态双半包**（node 半宿主服务 + client 半 UI），不用动态 cordis 双半插件（vm 沙箱非安全边界、无类型门禁）
- **i18n/主题**：`ctx.locale.register(ns, {zh, en})` + `ctx.locale.bind(ns)`；CSS Modules + `--dsw-alias-*` token
- 角色可见性：控制台页签按 `/api/auth/me` 返回的角色条件渲染；**权限真值始终以服务端为准**

## 8. 插件工程结构（草案）

```
dsh-multi-tenant/
├── package.json          # dsh manifest：dsh.client{platform:web,inject} + exports{".", "./client"}
├── cordis.patch.yml      # 组合 patch：插入 host/client 行
├── tsconfig.json
├── src/
│   ├── host/
│   │   ├── index.ts      # 主插件 apply：装配网关、服务、DB
│   │   ├── gateway.ts    # 认证网关（webServer 包装/内嵌反代）
│   │   ├── rpc.ts        # 自建 /mt 通道（ctx.connection.rpc.handle）：管理+租户 API
│   │   ├── auth/         # local / ldap / oidc 登录策略 + 会话签发
│   │   ├── rbac.ts       # 权限矩阵与校验
│   │   ├── quota.ts      # 配额检查与强制
│   │   ├── metering.ts   # 用量采集与计价
│   │   ├── audit.ts      # 审计日志
│   │   ├── db/           # SQLite（node:sqlite）schema + DAO
│   │   └── remote.ts     # 供 client 调用的通道 endpoint 定义
│   └── client/
│       ├── index.tsx     # client 插件：门禁/控制台/个人中心
│       └── components/…
├── test/
└── docs/
```

- **构建**：`"bundle": "tsdown"`（参考已装 client 包的产物格式：`window.__ModuleLoader__.load({id, factory})` lazy-CJS；React/Cordis/ui-slots 走 shell 静态表不打包；tsdown client preset 未随安装发布，需按 `dsh-client-ui-*` 的 `lib/client.js` 基准复刻，或参考 voice-plugin 手写 bundle 的方式兜底）
- **安装**：`dsh plugin --profile web add <package>`（或 profile node_modules 软链 + patch 行）
- 配置 schema：schemastery/zod；默认值出厂可用（bootstrap 管理员）

## 10. 风险与待决策点

1. **认证网关插入方式**：webServer 包装（依赖激活顺序，待报告 02 确认）vs 内嵌反代（稳但代码多）
2. **远程访问**：已确认 CLI 拒绝只限 flag 路径——patch/env 覆盖 `webserver` 行配置绑定 `0.0.0.0` 可行；公网场景推荐反代 TLS（形态 A）
3. **租户模型语义**：真多租户（租户间全隔离）还是"多用户单租户"起步 —— 需用户确认
4. **隔离深度**：v1 会话/权限/数据层逻辑隔离（`SessionId` 前缀 + 映射表 + 网关拦截）；**进程级隔离 DSH 不提供**（同 UID 同权限），需外部手段（容器/独立 DSH_HOME）——需用户知悉接受
5. **"管理员有审计角色权限"** 语义确认（管理员继承审计权限 vs 可授予他人审计角色）
6. **计价口径**：默认价格表（DeepSeek 官方价）+ 币种
7. **DB**：node:sqlite（已定，风险低）
