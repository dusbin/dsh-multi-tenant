# 第二期（V2）功能规划

> 本文汇总本项目一期（M1–M7 + 逃生通道/备份）之后**未完成、建议与暂缓**的工作，
> 作为二期迭代的需求池。来源：`docs/状态.md` §9、`docs/部署.md`、`docs/方案.md` §1.2/§8、
> 各里程碑验收记录与本会话建议。每条标注动机/来源，并按优先级 P0（推荐先做）/P1/P2 归类。

---

## 一、产品功能

### P0：用量统计按模型聚合
- 现状：`usage_records.model` 恒为空（采集未接模型/提供方），统计视图无"按模型"维度
- 动机：成本归因、模型使用分析（方案 §6.3 原计划含按模型聚合）
- 做法：计量时从会话最近一次 `assistant/message`/`request/header` 取 `provider/model` 写入记录

### P0：请求数精确统计
- 现状：`request_count` 为近似值（每次"有增量"的计量扫描计 1）
- 动机：会话/用量统计的口径准确性（方案 §6.3 请求数维度）
- 做法：按 `turn/start` 事件或 `request/header` 计数（`assistant/chunk` 去重规则已具备）

### P1：用量统计 CSV 导出
- 现状：审计有 `audit.export` CSV，用量仅有 `/mt usage.summary`（JSON）
- 动机：管理员/审计员对账与归档（方案 §5 导出统计）

### P1：自助找回密码 / 邮箱验证
- 现状：忘记密码仅靠主机侧 CLI / 环回恢复通道（无自助流程）
- 动机：降低运维依赖（`docs/部署.md` 逃生通道 SOP 的补充）
- 做法：可配置邮件网关（SMTP）→ 重置链接/一次性令牌（Token 复用 `auth_sessions` 机制）

### P1：会话管理增强（用户侧）
- 现状：只有管理员"强制下线"（`user.revokeSessions`）；用户不能查看/结束自己的其他会话
- 做法：`/mt auth.sessions`（本人会话列表 + 主动下线）；管理员侧增加"查看某用户在线会话"

### P2：金额计价与账单（D5 暂缓项）
- 一期按用户决策 D5 **仅 token、不做金额**；二期可选：模型价格表 → 金额折算与账单导出
- 依赖：先完成"按模型聚合"（P0）

### P2：用户自助注册 / 租户邀请码
- 现状：用户均由管理员创建（`user.create`）
- 做法：租户开启邀请码 → 自助注册（默认角色 user，可设默认配额）

### P2：配额告警通知
- 现状：配额超限即拒绝（`quota-exhausted`）+ 审计，无提前告警
- 做法：接近阈值（如 80%）时审计/日志告警，二期可接通知渠道

## 二、安全加固

### P0：登录页真实浏览器人工/E2E 验收
- 现状：协议级冒烟已覆盖，但登录页 UI（登录/恢复/LDAP/SSO 按钮、错误态）未经真实浏览器验收
- 做法：Playwright E2E（登录/退出/bootstrap/recovery/控制台页签）+ 人工过一遍明暗主题

### P1：多因子认证（TOTP）
- 动机：管理员/审计员账号的强认证（逃生通道只恢复密码，MFA 独立）
- 做法：`auth.mfa.enabled` 可配置；登录后二次校验；会话标记 mfa 通过

### P1：会话策略细化
- 现状：固定 14 天有效期、同账号多端不限
- 做法：可配置过期策略（绝对/滑动）、同账号最大并发会话数、设备指纹可选

### P1：密码策略可配置
- 现状：强度固定"≥8 字符"（`validatePasswordStrength`）
- 做法：长度/复杂度/历史密码/有效期可配置；强制改密

### P2：OIDC 会话刷新（refresh_token）
- 现状：OIDC 仅登录时校验 ID token；本地会话到期后需重新 SSO
- 做法：存储 refresh token（加密）→ 本地会话续期

### P2：LDAP/OIDC 属性同步
- 现状：LDAP/OIDC 仅在登录时映射一次（角色/邮箱不会同步变化）
- 做法：定期或登录时按目录属性刷新 email/displayName（角色仍由本地管理员管理）

### P2：审计日志保留策略
- 现状：`audit_logs` 只追加、无归档/清理
- 做法：可配置保留天数/容量 → 归档（导出）后清理

### P2：导出文件加密
- 现状：备份 JSON 含密码哈希，仅靠文件权限保护
- 做法：`export --encrypt`（口令派生密钥加密）；导入时解密

## 三、运维与交付

### P0：发布 npm 并正式安装
- 现状：本地目录安装已验证（`dsh plugin add <path>`）；未发布 registry 包
- 做法：`npm publish`（`dsh` bundle 声明已就绪）→ `dsh plugin --profile web add dsh-multi-tenant`；
  版本/CHANGELOG；`--trusted-host` 与版本演进兼容性说明

### P0：生产强隔离部署方案
- 现状：逻辑隔离（D1/D6 已确认）；进程级隔离 DSH 不提供（方案 §8、部署.md 安全边界）
- 做法：输出"每租户独立容器 / 独立 DSH_HOME / 独立 OS 用户"部署模板与成本对比

### P1：真实企业目录集成验证
- 现状：LDAP/OIDC 用自建 mock 完成协议级验证（`test/ldap-server-mock.mjs`、`test/oidc-server-mock.mjs`）
- 做法：对接真实 LDAP（AD/OpenLDAP）与 IdP（Okta/Keycloak/Entra）做回归；补充常见目录的
  `userFilter`/`attributes` 配置样例

### P1：CI
- 做法：GitHub Actions：`npm test`（Node 22/24）+ `node --check` client bundle + 冒烟脚本

### P1：DSH 特权方法远程化（可选）
- 现状：`settings.*`/`credentials.*`/`host.*` 对远程用户恒 403（DSH 原有限制）
- 做法：需要时走方案 §3.2 路径 B（组合级替换 connection 行，fork）——成本高，评估后再定

### P2：i18n 与文档完善
- 现状：UI 文案内联 zh/en；README/部署文档为中文
- 做法：接入 `ctx.locale` 完整命名空间；README 英文版；`docs/路线图-v2.md` 同步

### P2：多机 HA / 多实例
- 现状：单进程单所有者（DSH 存储形态约束，跨进程共享存储不支持）
- 做法：需存储层升级（共享 SQLite 加锁协议或外部 DB），成本高；先以"单机+备份"为准

### P2：SAML
- 现状：仅 OIDC（D2 未含 SAML）
- 做法：评估 `samlify` 等；通常经 IdP 网关转 OIDC 更省

## 四、技术债与优化

### P1：会话归属信封改写的版本跟进
- 现状：网关改写依赖对 session 域端点集的认知（`enforceSessionOwnership`），DSH 版本升级需跟进
- 做法：增加端点集清单的测试夹具（按 DSH 版本），升级时回归

### P1：计量精确性与恢复
- 现状：`session_meter` 基线在进程重启后对"已在跑的会话"只做首见基线（不补历史用量）
- 做法：重启后对持久会话日志回放补记（用 `tokenMeter.measure()` 对存量会话做一次基线+补记）

### P2：配置校验与文档化
- 现状：`resolveConfig` 深合并无 schema 校验（拼写错误静默忽略）
- 做法：引入 schemastery schema + 启动时校验 + 未知键告警

### P2：性能
- 现状：计量定时全量扫描 `ctx.sessions.list()` + `stateOf`（每会话 O(surface)）
- 做法：只扫描"最近有事件"的会话（订阅 `session/event` 增量触发），或接 `tokenMeter` 事件流

## 优先级说明

- **P0**：影响正确性/安全/可用性的收尾（模型聚合、请求数、UI 验收、发布、强隔离方案）
- **P1**：明确的体验或安全增益（找回密码、MFA、会话策略、CSV、CI、目录集成）
- **P2**：按业务需要取舍（金额、注册、SAML、HA、加密导出等）

> 一期已交付的能力见 `docs/状态.md`；二期范围可按本文档逐项评审排期。
